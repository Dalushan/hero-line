# 《英雄防线 / Hero Line》小游戏 设计方案 v0.1

> 平台待定版 · 2026-10-28
> 玩法原型：敌方出兵口 → 进攻路线 → 我方防守阵地 → 我方基地（生命值归零即失败）
> 支线玩法：每 5 波二选一支援（英雄 + 随机装备），已选过的英雄不再重复出现

---

## 0. TL;DR 决策摘要

| 决策项 | 结论 | 理由 |
|---|---|---|
| 目标平台 | **待你确认**（微信小游戏 / PC-Mac 独立版 / Web / 原生 App） | 引擎选型的唯一决定性因素 |
| 引擎（微信小游戏） | **Cocos Creator 3.x + TypeScript** | 小游戏发布链路最顺、2D 动画管线成熟、国内生态完整 |
| 引擎（PC / Steam / itch） | **Godot 4.x + GDScript** | 免费、导出干净、体积小、迭代快 |

### 1.2 各平台的最终推荐

**A. 目标 = 微信小游戏（最贴合"小游戏"语义）**
Cocos Creator 3.x + TypeScript。
- 一键导出微信小游戏，接微信开放能力（登录/排行榜/分享/激励视频）成本最低
- Spine 骨骼动画直接内建，英雄/小兵数量多时性能与美术成本都低
- 包体用 Asset Bundle 分包 + CDN 远程资源解决 4MB 限制
- 备选：微信官方 Unity 小游戏插件（生态更熟，但构建慢、包体大）

**B. 目标 = PC / Mac 独立版（Steam、itch.io）**
Godot 4.x + GDScript。
- 导出干净、无运行时依赖、体积小、Steamworks 有官方 GDExtension
- 2D 完全够用，自带 TileMap / AnimationTree / 粒子
- 缺点：微信小游戏要另找移植方案（所以只做 PC 时选它）

**C. 目标 = 先验证玩法（推荐的第一步）**
PixiJS（渲染）或 Phaser 3（带完整场景/物理/输入框架）。
- 半天起项目，浏览器直接跑，改一行刷新即见
- 核心逻辑写纯 TS，与 Cocos/Godot 端共用同一份 `core/` 目录
- 唯一代价：与微信小游戏/Godot 的美术资产（Spine/Godot 场景）需重做一次

**D. 全平台（Steam + iOS/Android + 微信）**
Unity 2022 LTS + WeChat MiniGame 插件 + Addressables。
- 只有在确定要全平台、且你已熟悉 Unity 时才选

### 1.3 不推荐的选项
- **Flutter**：UI 层强，但游戏渲染管线（粒子、Sprite 批次、Shader）不匹配，动画资产管理弱，会在中期拖后腿
- **原生 Android/iOS（Swift/Kotlin/Canvas）**：包体和设备适配成本过高，不适合单人
- **纯 Canvas 2D 手写**：只在"纯 Web 嵌入已有站点"这个特定场景考虑

### 1.4 无论选哪个引擎都要遵守的架构原则（最重要的一条）

```
core/        ← 纯 TypeScript，零引擎依赖，零 DOM 依赖
              网格/寻路、波次、战斗、伤害、经验归属、掉落、抽卡、数值
              ↓ 单测 + 无头模拟（跑 1000 波看曲线）
game/        ← 引擎适配层（对引擎的唯一翻译层）
              实体、渲染、输入、动画、音效、UI 事件
data/        ← JSON 配置表（英雄/装备/波次/敌人）
```

好处：
1. 核心逻辑可以用 Vitest 单测，不需要跑引擎
2. 可以写**无头数值模拟器**，一天跑完 1000 波、100 局，AI 托管，自动输出"第几波开始卡关""金币是否溢出""经验曲线是否平"
3. 换引擎只重写 `game/` 层，核心资产（数值表、规则）零损失

## 2. 玩法系统详细设计

### 2.1 战场结构

```
┌───────────────────────────────┐
│  [敌方出兵口 Spawn]            │   网格 20 列 × 14 行（cell = 64px）
│         ↓ 进攻路线             │   ├ 通路 cell（敌人可走）
│    ┌──────────────┐           │   ├ 建造格 cell（可放英雄/防御塔）
│    │  我方防守阵地 │           │   └ 装饰/障碍 cell
│    └──────────────┘           │
│         ↓                     │
│      [我方基地]                │   基地有 HP（1000），漏怪扣血
└───────────────────────────────┘
```

**关键设计决策**

| 项 | 决策 | 说明 |
|---|---|---|
| 地图形态 | 固定单路径（首版）→ 中期加入多条支路/环形 | 单路径最省实现成本，且符合你草图 |
| 敌人寻路 | 网格 A* + 流场（Flow Field） | 塔防放塔会改路，需要动态重算 |
| 放塔合法性 | ① 不能放在通路格 ② **放塔后必须保证基地仍可达**（BFS 校验） | 经典"堵路"翻车点，必须做 |
| 建造格数量 | 约 40~60 格 | 决定布防自由度 |
| 相机 | 固定单机位，不做平移缩放（首版） | 省一大块输入/相机代码 |

**"堵路检测"实现（必须写）**
```ts
function canPlace(grid: Grid, cell: Cell): PlacementResult {
  if (!cell.buildable) return { ok: false, reason: '该格不可建造' };
  const saved = grid.cellAt(cell);
  grid.setBlocked(cell, true);                 // 临时占用
  const reachable = grid.bfsReachable(GRID.baseCell);  // BFS 判可达
  grid.setBlocked(cell, saved);                // 还原
  if (!reachable) return { ok: false, reason: '会封死通往基地的路线' };
  return { ok: true };
}
```

### 2.4 经验归属系统（★ 最容易翻车的地方，单独立项）

你的规则是"**最后击杀敌方小兵的英雄才有经验**"。纯 Last-Hit 在塔防里体验很差（后期多塔 AOE/溅射会互相抢人头，AOE 塔永远拿不到经验），所以要设计成 3 方案的混合：

| 方案 | 规则 | 评价 |
|---|---|---|
| A. 纯 Last-Hit | 只有造成最后一击的英雄拿经验 | 实现最简，但 AOE 塔完全废 |
| B. 范围分享 | 击杀瞬间，射程覆盖该死亡点的存活英雄按权重分经验 | 公平但"远程塔白嫖"，无归属感 |
| C. **Tag & Carry**（推荐） | 英雄攻击小兵时打标记（类似 LOL），小兵死亡时标记者获得全部经验；标记保留 3s，标记者死亡/离场则转移给最近标记者 | 归属感强、鼓励集火、跨塔协同自然 |

**推荐实现（C 为主 + A 保底）**
```ts
// 每帧/每次攻击：打标记
function applyAttack(attacker: Hero, target: Enemy) {
  target.tag = { heroId: attacker.id, at: now, weight: attacker.expWeight };
  // 标记可叠加多来源，取最近一次
}

// 小兵死亡：结算经验
function onEnemyDeath(enemy: Enemy) {
  const exp = enemy.expValue;
  const tag = enemy.tag;
  const tagHero = tag ? heroes.get(tag.heroId) : null;
  const lastHit = heroes.get(enemy.lastHitBy);

  if (tagHero && tagHero.alive && now - tag.at <= 3.0) {
    tagHero.gainExp(exp * 1.0);          // 标记者拿全额
    if (lastHit && lastHit.id !== tagHero.id) {
      lastHit.gainExp(exp * 0.25);        // 最后一击保底 25%
    }
  } else if (lastHit) {
    lastHit.gainExp(exp);                 // 兜底：最后一击者全额
  } else {
    // 极端情况（塔 AOE 秒杀且无标记）→ 归给最近伤害来源，或不发经验
    expPool.gain(exp);
  }
}
```
> 这段逻辑是纯 `core/` 代码，单测覆盖 8 个边界用例即可（标记者死亡、标记过期、AOE 秒杀、重复击杀、标记者换位等）。

### 2.5 支援二选一（每 5 波一次，不重复）

**规则定义**
- 每 5 波（第 5、10、15、20、25、30 波前）暂停战斗，弹出 2 个候选卡牌
- 每个卡牌 = 1 名英雄 + 1 件装备（装备随机）
- 玩家二选一，选中的英雄/装备加入本局阵容，**该英雄此后不再出现**
- 未选中的英雄**不进入已选池**（可以以后再出）→ 保证"不重复出现"只约束选中的

**候选池生成算法**
```ts
function rollSupportCards(state: RunState, rng: RNG): SupportCard[] {
  const available = HERO_POOL.filter(h => !state.selectedHeroIds.has(h.id)); // 未被选过的
  const weights = available.map(h => ({
    hero: h,
    w: h.rarityWeight * (state.wave >= 20 && h.rarity === 'rare' ? 1.5 : 1),
  }));
  const picks = weightedSample(weights, 2, rng);   // 不放回抽样，保证两卡不同
  return picks.map(p => ({
    heroId: p.hero.id,
    itemId: rollItem(rng, p.hero),                 // 装备随机，按英雄类型倾向
    level: 1,
  }));
}
```
**要点**
- 随机数用**可复现种子**（`runSeed`），便于复现 bug 和无头模拟
- 装备按英雄类型加权：物理 → 攻速/攻击力；法系 → 法强/智力；坦克 → HP/护甲
- 稀有度：普通(60%) / 精良(28%) / 稀有(10%) / 传说(2%)

### 2.7 经济与局内商店

```
金币来源：小兵击杀（8×1.06^w）、波次结算奖励、支援卡牌按稀有度给 100~800 金
金币用途：① 局内商店买英雄/装备/Buff ② 英雄升级消耗？→ 否，升级只吃经验
```
建议**商店只卖"Buff/补给"和"装备"**，不买英雄（否则与二选一系统冲突、稀释决策）。
商店每波结束刷新 3 件，30 金保底递增。

### 2.8 关卡与难度

- 一关 = 30 波 = 约 8~10 分钟（一局长度适合小游戏）
- 5 章，每章 30 波 + 一个 Boss（每 10 波一个大招节奏）
- 难度：普通/困难/噩梦 = 敌人 HP×1 / ×1.6 / ×2.4，支援卡牌数 +0/+1/+1（困难多给一张自选）
- 局外成长：解锁英雄池、永久天赋（每级 +1% 攻击等），用"金币+账号"做解锁，**不做数值碾压**（避免小号被碾压）

### 2.9 完整状态机

```
Boot → 主菜单 → 选关/开局 → Battle
Battle 内部：
  WavePreparing (布防期 8s, 可加速/商店)
    → SupportDraft (第5/10/15...波触发, 暂停)
    → WaveRunning (敌人推进)
    → WaveCleared (结算金币/经验/掉落)
    → 下一波 …
  → Victory / Defeat → 结算页 → 主菜单
```
> SupportDraft 是**可打断/可跳过的**（付费跳过得金币），避免拖节奏。

**事件总线示例**（core 广播，game 层订阅，core 完全不知道引擎存在）
```ts
export type GameEvent =
  | { type: 'enemy_killed'; enemy: EnemyView; killerId: string }
  | { type: 'hero_leveled'; heroId: string; level: number }
  | { type: 'wave_started'; wave: number }
  | { type: 'support_draft_opened' }
  | { type: 'base_damaged'; hp: number };

export const bus = new EventBus<GameEvent>();
```

**战斗循环（固定步长）**
```ts
// 固定 60Hz 逻辑步 + 插值渲染，避免不同帧率下数值不一致
const FIXED_DT = 1 / 60;
let acc = 0;
function frame(dt: number) {
  acc += Math.min(dt, 0.25);           // 掉帧保护
  while (acc >= FIXED_DT) { core.step(FIXED_DT); acc -= FIXED_DT; }
  render(acc / FIXED_DT);
}
```

## 5. 性能与包体

| 问题 | 方案 |
|---|---|
| 敌人/子弹对象过多导致 GC 抖动 | **对象池**（敌人 300+、子弹 500+ 全池化，零运行时 new） |
| 范围查询 O(n²) | 空间哈希网格（cell 30×30 px），范围查询只查邻近格 |
| 多英雄同帧 AI 决策 | 统一 tick，按 `nextActionAt` 错峰，减少同帧 spike |
| 微信主包 4MB 限制 | Cocos Asset Bundle 分包：首包只放启动必需资源，英雄/关卡/音频走 CDN 远程资源 |
| 图片体积 | 图集打包 + WebP/ETC 压缩，UI 用 9-slice |
| 音频体积 | 短音效用 mp3/ogg 压缩，背景音乐单独放 CDN，首包不带 |
| 首屏时间 | 资源预热 + 分帧加载（每帧加载 N 个资源，避免长卡顿） |
| 低端机帧率 | 自适应画质：帧率低于 45 自动关粒子/降特效 |

## 6. 测试策略

1. **单元测试（Vitest，覆盖 core）** — 必测用例：
   - 寻路：BFS 可达性、放塔封路检测、放塔后重算路径
   - 伤害：护甲/魔抗减伤、暴击、伤害类型克制
   - 经验：Tag & Carry 的 8 个边界用例
   - 抽卡：不重复约束、权重分布（10000 次采样 chi-square 检验）
   - 数值：波次 30 波 HP/金币/经验单调性
2. **无头数值模拟器**（`tools/sim`）— 核心护城河
   - 固定种子 + 简单 AI（优先放高 DPS 英雄、按最优时机用支援卡）
   - 跑 1000 局，输出：平均通关波次、死亡波次分布、经济曲线、资源是否溢出/不足
   - **目的**：改数值不用手玩，直接跑模拟看曲线，一轮 30 秒
3. **引擎侧冒烟测试**：每关自动跑一局，校验胜利条件与 UI 状态机无死锁
4. **真机测试**：iPhone SE / 低端安卓 / iPad，帧率 ≥ 50，长时运行内存不涨

## 8. 美术与音频资源策略

**原则：玩法先跑通，美术后替换。** 所有 P0~P6 阶段用程序化图形（矩形/圆形 + 颜色区分），只在 P7 替换。

| 资源 | 方案 | 成本 |
|---|---|---|
| 英雄立绘 | 原创 Q 版像素/扁平风；AI 生成初稿 + 人工修 | 高（12 个角色） |
| 小兵 | 单张图 + 颜色变体（3~4 种） | 低 |
| 技能特效 | 粒子 + 着色器（Cocos/Godot 内置） | 中 |
| UI | 9-slice + 图标集 | 中 |
| BGM | 授权曲库或 AI 生成 | 低 |
| SFX | 现成免费音效包 | 极低 |

**⚠️ 版权红线（务必遵守）**
- Valve 拥有 Dota2 的英雄形象、物品图标、商标与音频的版权
- Valve 官方"Art Assets"包仅允许用于 Dota2 模组，**不可用于商业发行**
- 合规做法：**只借鉴玩法机制与数值思路，角色全部原创**（例如"剑圣"→"斩光者"，"跳刀"→"相位匕首"）
- 代码层面：把 `dotaId` 字段保留为内部占位映射没问题，但**游戏内显示名、图标、美术必须原创**
- 如果仅自用/学习不做商业化，容忍度高；但发布前必须替换
